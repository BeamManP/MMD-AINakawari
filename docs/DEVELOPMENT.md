## 使い方
1. （11-07 まで、ここで低負荷／高速の動作モードを選んでいた。いまは選ばない。下の「文の読み取り」）
2. MMD のメニュー「MMDKimodo」（ヘルプの右）→「Kimodo の窓を開く」。初回は Python の起動で数秒かかる
   - 窓は MMD ごとに 1 つで、その MMD の持ち物（MMD の上に出て、MMD を最小化すると一緒に隠れる）。生成と「元に戻す」はその MMD に効く
   - 窓の × は隠すだけ。メニューからまた出る。MMD を閉じると、その MMD の分は一緒に終わり、全部閉じると MMDKimodo（Python）も終わる
   - `MMDKimodo.cmd` は手で起動する時用（一番手前の MMD の窓を開く）
3. MMD のモデル欄でモデルを選び、ポーズを付けてキーを打つ（例: 0F・30F・60F）。**0F にもキーがあること**。窓の一番上に「選択中のモデル：…」と出る（PMX の場所は MMD から読むので指定は要らない。PMD のモデルは非対応）
4. 窓のタブで作り方を選んで「生成」。10 秒前後で MMD に入る（11-04 昼の高速化の後。その日の朝は 55〜63 秒）
   - **プロンプトで作る**（Kimodo）: 「やりたいこと」を選び、プロンプト（英語）を入れる
   - **中割り**（MotionBricks）: プロンプトは要らない。キーとキーの間（17〜57F）をつなぐ
   - 初回だけ、Kimodo・MotionBricks を常駐させる読み込みで 10〜15 秒ほど余分にかかる（下の「常駐」）
5. 気に入らなければ「元に戻す」、または プロンプト・seed を変えてもう一度「生成」（前回の元のキーから作り直す）

**MMD の右下の「AIナカワリ簡易操作」パネル**（11-04 夜。`mmd_plugin/nakawari_panel.cpp`・`mmd_ainakawari/panel.py`）: MMD の下の段の操作パネルの右の空き地に、プラグインが MMD の子の窓としてパネルを置く。三行式（11-05 マスター）: 1 行目にモード選択（プロンプト／中割り）と範囲の字（「選んだキー 90〜120F」「キーを選んでいません」「全部のキー」。11-05 にチェックをやめた。範囲の切り替えは窓だけ）、2 行目にプロンプト 1 行（区間は `run / 45: stop` のように「 / 」でつなぐ。窓では行に分かれる）、3 行目に生成・元に戻す・詳細（窓を出す）、下に状態の 1 行。中割りの時はプロンプト欄とサンプルを灰色にする（字は残す）。**プロンプト欄の下の「サンプルから選ぶ」**（11-05 マスター。英語が苦手な人向け）: 押すと種類ごと（歩く・走る／止まる・立つ／身ぶり／ダンス／スポーツ・アクション／気持ち）に「前へ歩く：A person walks forward.」の形の一覧が出て、選ぶと英語の文がプロンプト欄に入る。一覧は `mmd_ainakawari/prompt_samples.txt`（6 種類・43 個。文は Kimodo のデモの例文と同じ「A person ＋ 今の形の動詞」）。押すたびに読むので、書き換えればすぐ反映される。窓のプロンプトの下にも同じ「サンプルから選ぶ ▼」がある（`mmd_ainakawari/samples.py` が同じファイルを読む）。窓では、最後に打っていた行に入る（まだ触っていない・その行を消した時は「始め」の行）。タイムラインでキーを選んで、すぐ横で生成できる
- パネルは部品を並べるだけで、中身は窓（`App._sync_panel`）が 0.5 秒ごとに読み書きする。入力（プロンプト・切り替え・チェック）は変わった方からもう一方へ写し、表示（状態・範囲の字・ボタンの押せる押せない）は窓からパネルへ。別のプロセスの部品なので WM_GETTEXT などは Windows が写してくれる。MMD が忙しい間に窓が固まらないよう、送る時は 0.2 秒の期限付き（SendMessageTimeout）
- ボタンはプラグインが Hub に知らせる（`AINakawari.Panel.v1`・lparam がボタンの番号）。パネルに中身を出すため、MMD の起動時にプラグインが Python の窓を隠したまま立ち上げる（`--attach`・`AINakawari.Attach.v1`）。その時はまだ MMD の窓が見えておらず `list_windows` に出ないので、見えるまで 30 秒待つ（待たずにすぐ終わっていた）。MMD の起動から 1.2 秒でパネルと窓がそろう（11-04）
- 大きさと位置は MMD の下の段のパネルに合わせる: 上端は各パネルの見出しの「－」ボタン（14×14）の 2px 上、下端は窓の下端の 2px 上（高さ約 155px）、横は 240px、字は MMD の字体（ＭＳ Ｐゴシック 12）を高さ 10 にしたもの。ボタンだけは MMD のボタン（再生・登録など）と同じ高さ 12 のまま（11-05 マスター）。部品は作ってから動かすので、動かす時に古い絵を写さない（SWP_NOCOPYBITS）・並べたら子まで描き直す・WM_PRINTCLIENT に背景を描く（モード選択が、マウスを乗せるまで灰色のままだった）。最初は「カメラ編」ボタンの下＋26px を上端にして空き地いっぱいに広げていたので、カメラ用のモードでは 673×330px になった（11-04 マスター「クソデカサイズ」）
- **プロンプト欄に打っている間は、MMD のショートカットが効かない**（11-05）: MMD にはキーの表（アクセラレータ）が無く、キーの状態を直接見る関数も使っていない（GetKeyState だけ）。キーの知らせを、メッセージの取り出しの所でまとめて見てショートカットにしているらしい。なので、プロンプト欄宛てのキーの知らせは、プラグインの受け口（WH_GETMESSAGE）でパネルが欄に届けてから WM_NULL にして MMD に返す（`NakawariPanel::filter`）。ただし MMD は文字のショートカット（i など）を GetKeyState で「今押されているか」見ていて、知らせを WM_NULL にしても押されている記録は更新されるので、それだけでは i が効いた（11-05 マスター）。なので MMD の実行ファイルが呼ぶ GetKeyState を差し替え（呼び先の表 IAT を書き換える）、プロンプト欄にフォーカスがある間は「押されていない」と答える。欄そのものは user32 の中で GetKeyState を呼ぶので影響しない。MMD を閉じる時に戻す。Enter で生成・Esc でフォーカスを外す。欄の外（MMD が自分で描くタイムラインや 3D 画面は、押してもフォーカスが動かない）を押した時と、パネルのボタン・チェック・モード選択を使った後は、フォーカスを MMD に戻す
- **カメラ・照明・アクセサリのモード（カメラ用）では出さない**（11-05 マスター）。3D 画面の下の「カメラ編／モデル編」ボタン（部品番号 536）は今と逆のモードの名前を出すので、「モデル編」と出ていればカメラ用のモードとして隠す。空の場面・Tda ミクを読み込んだ後・ボタンで行き来、で隠れる／出るを確かめた。隠す時にプロンプト欄にフォーカスがあれば MMD に戻す（GetKeyState の差し替えで、ショートカットが止まったままにならないように）
- 窓が狭くて入りきらない時は、MMD のほかのパネルと同じく右端で切れて見える（右に 40px も見えない時と、高さ 110px 未満の時だけ隠す）。ボタンは左から並ぶので、切れても生成は押せる（横 1400px の窓で確認）。11-03 にボタン 1 つで作った時は「メニューと同じ」で外したが、範囲を選んだキーで決めるようになったので、生成・元に戻す・プロンプトを置いて戻した

窓の並び（11-04 に作り替え・昼にタブに分け、午後に上下固定にした）: **上**（選択中のモデル）と**下**（範囲・生成／元に戻す・状態 1 行・ログ）は固定で、**真ん中のタブだけが伸び縮みする**。タブの中身が入りきらない時は、タブの中にスクロールバーが出る（`widgets.ScrollFrame`。ホイールはポインタの下の枠に効く）。窓の高さの下限は上と下が必ず見える高さ（Tda ミクの窓で 303px）。前は縦に積んでいたので、窓を低くすると下の「生成」から黙って切れていた（576×206 で生成が見えなかった）:
| 欄 | 中身 |
|---|---|
| タブ | **プロンプトで作る**（Kimodo。下の「やりたいこと」〜「詳しい設定」）／**中割り**（MotionBricks。「キーごとに止まる」「手首は普通の補間」だけ）。開いているタブのやり方で生成する。タブを切り替えても窓の大きさは変えない |
| やりたいこと | **キーの間を埋める**（打ったキーのポーズを守る・長さは最後のキーまで）／**続きを足す**（範囲の終わり＝全部なら最後の体のキーの姿勢から、長さのフレーム数だけ後ろに足す。下の「続きを足す」）／**プロンプトだけで作る**（守らない・長さ必須）／**センターに合わせて作る**（埋めると同じ範囲で、キーのポーズは使わず、毎フレームの腰をセンターに合わせる。下の「センターに合わせて作る」） |
| 範囲 | 全部 ／ **選んだキーの間**（既定。MMD のタイムラインで選んだキーの、最初から最後までのフレームを作り直す。どのボーンのキーでもよい。窓に今の選び方の範囲が出る。キーを 2 つ以上選んでいない時は「生成」を押せない。選んでいない時にうっかり全部を作り直さないように。11-05 マスター） |
| 最後のキーで止まる | 最初からオン。横の「なめらかに（MotionBricks）」も最初からオン（MotionBricks が入っている時だけ押せる）。下の「最後のキーで止まる」 |
| プロンプト | 行ごとに「何フレームから」と「動き」。最初の行は範囲の始まりから（フレームの欄は無い）。「＋ 今のフレーム（NF）で区切る」で MMD の今のフレームの行が増える。保存は前と同じ「45: …」の形 |
| ログ | 下の「ログ」で別の小さな窓を開く（本体の並びを押し出さない。× は隠すだけ） |

- **続きを足す**（11-07 作り替え・`pipeline.extend_plan`）: 前は長さが「最初のキーから数えた全部の長さ」で、範囲が「選んだキーの間」だと長さの欄が効かず、埋めると同じ動きになっていた（30〜60F を選んで 100 と書いても 30〜60F しか作らない。マスター「ぱっとしない」）。今は長さを「足すフレーム数」にして、範囲の終わり S（全部なら体と全ての親の最後のキー）から S+1〜S+N を作る。仕組みは範囲の作り直し（`frame_range=(S, S+N)`・手前 3 フレームの文脈）と同じで、`extend=True` の時は区間の中の体・手足の IK のキーを目印にせず上書きする（全ての親は書き戻さない骨なので目印のまま）。後ろにもキーがあれば S+N の姿勢は MMD のままでつなぐ。続きの終わりにキーは無いので「最後のキーで止まる」は使わない。上書きされる体のキーは、窓が 1 秒ごとに MMD のメモリから骨ごとのキーのフレームを読んで（`MotionReader.scan`）、長さの欄の下に赤い字で出す（「範囲内に上書きされるキーフレームがあります」。11-07 マスター）。作り直しの区間の記録（span）には足す長さを入れない（長さを変えて押し直すと、前回足した所を元に戻してから足し直す。入れると、前回足した所のさらに後ろへ足すことになる）。確かめ: `tests/check_extend_1107.py`（作り物 14 件）
- **中割り**（11-04 追加・`nakawari.py`）: 体のキーとキーの間を、前のキーから次のキーへ MotionBricks で 1 回ずつ作ってつなぐ。プロンプトも文の読み取りも使わない
  - 「キーごとに止まる」オフ（既定）: 次のキーへ 1 フレーム進んだ姿勢も目標に渡し、その速さでキーを通る。オン: 目標の姿勢 1 つで、各キーで止まる
  - MotionBricks の 1 回は 17〜57 フレーム。キーの間がそれより短い・長い所は作らず MMD の補間のまま（`Job.mmd_frames`、書き戻さない）。ログに出る
  - **手首**: MotionBricks は手首をキーの差より大きく回すことがある（11-04、VPD の立ちポーズ 10 個・30F おきで、キーどうしの差 20° の区間を合計 379°・1 フレームで最大 131°）。「手首は普通の補間」オンで、手首だけキーの間を球面の補間でつなぐ（最大 3〜5°/フレーム。ひじ・体は変わらない）
  - 全ての親だけ・手足の IK だけのキーは使わない（MotionBricks は途中の目印を知らない）

- プロンプトは Kimodo の説明書（Best Practices）どおり「A person …」で始め、中くらいの細かさで書くのがよい（「A person walks.」でも短すぎる例として挙がっている）。区間に分ける時は、各区間の文だけで意味が通るように書く

- 完全新規では体のキーのポーズは使わず、最初のキー（ふつう 0F）の場所・向き・床の高さだけを基準にする。0F の元のキーも書き換わる。MMD はモデルを読み込むと 0F に初期のキー（A ポーズ）ができるので、守るとそこから動き出してしまう
- 全ての親のキー（腰の通り道）は、チェックに関係なく使う
- **センターに合わせて作る**（11-03 に「詳しい設定」のチェック「センターの動きを使う」として追加。11-07 にやりたいことの 4 つ目にした）: 毎フレームで、腰の世界の位置（センター・グルーブ・全ての親の補間込み）を XZ と高さの目印にし、キーのポーズは使わない（`use_keys=False, use_center=True`・長さなし。範囲はキーの間を埋めると同じで、範囲を選んだ時は始まり（と後ろに続く時は終わり）の姿勢だけ守って前後につなぐ）。センターの上下でリズムを付けて、ポーズと動きはプロンプトから作る用。前はチェックで、埋める・続きを足すと組み合わせると、体のキーのあるフレーム（センターのキーも体のキー）が全身のポーズごと守られ、「腰だけ守ってポーズは作る」にならなかった（11-07 マスター）。腰の高さは Kimodo 標準に無い制約を `tools/kimodo_gen.py` の `RootYConstraintSet` で足している（モデルの条件には入るが、後処理の合わせ込みは掛からない）
  - Kimodo だけだと腰の高さは「だいたい従う」止まり（センターだけ 15F 毎に沈む＋完全新規 120F・テキスト 5 で、ずれ 平均 4.2cm・最大 10cm、上下の相関 0.61。拍の間に Kimodo 自身の沈みも混ざる）
  - なので書き戻しで**センターの高さを目印ぴったりに上書き**し、足ＩＫは動かさない（差は MMD の IK が膝の曲げで吸収）。同じテストで上下の相関 0.99、一番沈むフレームが目印と全部一致（7, 22, 37, …, 112）、足首と足ＩＫの距離 最大 2.2cm
- 確認（11-03）: 0F だけの状態から長さ 150・`A person walks forward, stops, and waves with the right hand.` → 150 フレーム全部が埋まり、5 秒で前へ約 6m。カメラが原点近くの固定だと、前へ歩くプロンプトはカメラに突っ込む

- **プロンプトの差が出ない時は「テキストの効き」を上げる**。Kimodo の既定（テキスト 2・キー 2）だと、キーが 1 秒毎のダンスではプロンプトを変えてもほぼ同じ動きになる（11-03、4 プロンプトで骨の向きの差が平均 7〜12°）。回転のプロンプトで測ると、腰の向きの幅は 2・2 で 108°、5・2 で 159°、8・1 で 347°。最初のキーだけでも 2・2 では 4 秒で半回転しかしない
- 前回の生成の控えと結果は `work/last_run.json` に MMD ごと（プロセス番号と起動時刻）に残る。窓を開き直しても、作り直しと「元に戻す」が効く。MMD を開き直すと引き継がない（別の場面に古い控えを読み込ませないため）
- キーを手で直したい時は、先に「元に戻す」をしてから直す（生成後の毎フレームのキーが残っていると、それも全部キー扱いになる）

  - 当てはめ: 移動の X・Y・Z は軸ごとの値、回転は前後のキーの大円の上の割合を進み具合にして、制御点（0〜127）を探す。x1・x2 は 8 刻みの格子、y1・y2 は最小二乗。最後に MMD と同じ式で全フレームを確かめる。MMD の回転の補間は大円の上だけなので、外れる所と、端の値を越えて行って戻る所はキーを残す
  - 全身の確かめは **IK を解かない**。MMD で IK が動かす脚（足・ひざ・足首・つま先）は、骨の回転でなく足ＩＫ・つま先ＩＫの位置で見る。脚の骨の回転まで見ると、見た目に出ない所を守るためにキーが 1673 個に増えた（IK のボーンで見ると 1219 個）。IK を解くと 1 フレーム 0.044 秒（Tda ミク・8 割が IK）で 300F の確かめが 2 分かかったので、見る骨に効く骨だけを全フレームまとめて numpy で計算する（`Thinner._poser`。`MMDSkeleton.pose` との差 4e-16）

  - この 30〜90F は、Kimodo の手首・腕・足首がフレームごとに細かく揺れていて（回転の 2 階差の中央 2〜4°／フレーム）、揺れも保つので手首は 61 フレームに 56 個残る（とても粗くで 32 個）。揺れをならして減らすのは、動きを変えることになるので入れていない
  - IK をオフにしたフレームの脚は、IK のボーンの位置でしか確かめていない（脚の骨は骨ごとの許容差だけ）

- **範囲を「選んだキーの間」にすると、その範囲を作り直す**（11-04 夜。長いモーションの一部だけ作り直す時）。MMD のタイムラインで、最初と最後のキーを選ぶ（四角で囲む・Ctrl で足すなど。行はどのボーンでもよい）。選択はメモリのキーの最後の 4 バイトの印から読む（`mmd_memory.MotionReader.selected_frames`。1024 件ずつまとめて読み、734 個で 5ms）。最初は MMD の範囲選択の欄（タイムラインの下の開始〜終了フレーム）を読んでいたが、場所が分かりにくいのでキーの選択に替えた（11-04 マスター）。範囲の始まりの姿勢（MMD の補間込み）はいつもキーにし、終わりの姿勢は後ろにもキーがある時だけキーにして、外の動きにつなぐ。範囲の中のキーも通る（「プロンプトだけで作る」なら使わない）。範囲の端の外側 3 フレームの姿勢も渡して外の勢いをつなぐ（Kimodo にはキーとして渡して書き戻さない・中割りは MotionBricks の文脈にする）。長さの欄は使わない（範囲の終わりまで）。後ろにキーが無い範囲では、終わりの姿勢は決めずに作る。ただし終わりのフレームの全ての親・手足の IK のキーは目印にする（11-04 夜、全ての親だけで回って 75F で原点に戻る場面の 20〜75F で、75F の目印が抜けて戻らなかった。直して 75F のずれ 4cm）。Kimodo は 1 回 300 フレーム（10 秒）まで
  - 前は範囲の中のキーを絞るだけで、範囲の端は使っていなかった（30〜90F でキーが 45・60F なら 45〜60F だけ作っていた）
  - **元のキーの間に足したキーは、元の補間曲線をそこで分けた曲線を持つ**（`mmd_skel.split_interp`）。範囲の端に直線の補間のキーを足すと、範囲の外の動きの形が変わっていた（ゆっくり始まり・終わる曲線の場面で、範囲の外のずれ 3.9° と 8.7° → 0.03° と 0.13°。MMD の制御点は 0〜127 の整数なので、急な曲線では少しずれる）。「全部」の時の、最初・最後のキーのフレームに足すキーも同じ
- **区間ごとのプロンプト**（11-03 追加）: プロンプトの行ごとに、そのフレームから次の行までをその文で作る（Kimodo の multi_prompt）。最初の区間は範囲の始まりから、最後の区間は範囲の終わりまで。区間は 8 フレーム以上。例: 0〜44F 構えて踏み込む・45〜59F 右ストレート・60〜90F 余韻 → 60F（キーのポーズ）がインパクトになる。キーの無い区間で Kimodo が落ちる（空の制約で reshape）ので、`tools/kimodo_gen.py` の `_skip_when_empty` で空になった制約を飛ばしている
  - **区間は前から 1 つずつ作られ、各区間には自分のフレームの範囲のキーしか渡らない**（Kimodo の `kimodo_model.py` が制約を `crop_move(区間の始め, 区間の終わり)` で切り取る）。なので手前の区間は後ろのキーを知らずに動く
  - **2 つ目以降の区間の最初の 5 フレームは、前の区間の最後の 5 フレームを制約にして作り直す**。区間の始め（とその後 5 フレーム以内）にキーがあると、その制約とキーがぶつかり、後処理が無理やりキーに合わせて跳ぶ（11-04、走り→止まる→立つで 60F のキーと区間の始めが重なり、腰が 1 フレームで約 2m 跳んだ。区間の始めを 66F にずらすと消えた）
  - **区間の始めの直後（0〜5 フレーム後ろ）にキーがあれば、区間の始めをキーの次のフレームへ自動でずらす**（11-04 昼・`pipeline.snap_segments`。ログに出る）。キーが手前の区間の最後のフレームになり、手前の区間がキーへ向かって作る。試験台（2 つのシード）で、つなぎ目の腰の 1 フレームの動き 91〜293cm → 15〜23cm（ほかの所の走りと同じくらい）・キーのずれは 0 のまま。「センターに合わせて作る」時は毎フレームが目印なのでずらさない
- **最後のキーで止まる**（11-04 追加）: キーは「その瞬間にこの姿勢を通る」だけで、そこで止まる意味は持たない。走りなどは勢いのまま通り過ぎる（11-04、60F のキーを 3.5 m/s で通り、1.55m 先で止まった）。オンにすると、最後の体のキーの後ろ 10 フレームに「腰（と向き）はキーの位置から動かない」目印（Kimodo の腰の通り道の制約）を足し、Kimodo はキーの手前で減速して止まる（同じ場面で 60F での速さ 0.8〜1.0 m/s・行き過ぎ 0.05m 以下・跳び無し）。「キーの間を埋める」では作る範囲がキーで終わるので、裏で 10 フレーム余分に作らせて目印を置き、書き戻すのは最後のキーまで。キーの後ろに全ての親・手足の目印がある時と「センターに合わせて作る」時は止めない（`pipeline.prepare(stop_at_last_key=…)`）
  - ただし Kimodo だけだと**キーの 5 フレームほど手前で急に止まる**（11-04 マスター「ピタッと止まりすぎかも」。同じ場面で一番強い減速 26.6 m/s²）。止める目印をキーの後ろへずらす（+3・+5・+8F）・押し出す、は効かなかった。よその連携の工夫（「減速する腰の通り道」を 5 フレームおきの目印で渡す・Unity の連携の √(2×減速度×残りの距離)）も試したが、Kimodo が道の途中を飛ばして最後に急ブレーキし、33〜36 m/s² でかえって強くなった
- **なめらかに止まる（MotionBricks）**（11-04 追加）: Kimodo の結果の「最後のキーの手前 L フレーム」を、MotionBricks（NVlabs/motionbricks。今の 4 フレームと目標の姿勢 1 つから、そこへ着いて止まる動きを作る）の動きに差し替える（`smooth_stop.py`・橋渡しは `tools/mb_gen.py`）
  - L は 18〜57 の候補をまとめて作り（1 回の起動で 14 通り・5 秒前後）、腰の速さ（3 フレームならし）の一番強い加速・減速が小さいものを選ぶ。長いほど Kimodo の動き（プロンプトの動き）を多く置き換えるので、1 フレームあたり 0.05 だけ短い方を優先
  - 手前の体のキー・全ての親・手足の目印より前には伸ばさない（MotionBricks は途中の目印を知らない）。17 フレーム取れない時と、キーの 30〜10 フレーム手前の腰の速さが 1 m/s 未満（もともと止まり方の問題が無い）の時は Kimodo のまま
  - 確認（11-04・MMD に書き戻した下半身の速さ。走って 60F のキーで止まる場面・シード 2）: 「埋める」で一番強い減速 23.5 → 11.9 m/s²（12〜60F の 48 フレームを作り直し）、「続きを足す」（90F・区間 3 つ）で 14.9 → 9.5 m/s²（18〜60F）。キーの腰の位置とのずれ 0cm、キーの後ろへのつながりも滑らか（62F 0.31 → 65F 0.04 m/s）
  - その分、作り直した区間の前半は少し速くなる（決まったフレームに決まった場所へ着いて止まるので。Kimodo だけの 5.5 m/s → 6.2〜6.5 m/s）
  - 姿勢の付け替え: SOMA の 30 関節は名前も並びも同じ。MotionBricks の骨格（77 関節の USD）は基準の回転が 0 でないので「MotionBricks の世界の向き = Kimodo の世界の回転 × MotionBricks の基準の世界の向き」で付け替える。往復で回転のずれ 0.0000°・関節の位置の差（骨格の違いの分）最大 3.9cm
- **手足の IK だけのキーは「手足の目印」**（11-03 追加）: 手足を動かす IK（腕の IK・足ＩＫ。IK のボーンか目標の基準の位置が手首・足首に重なるものを自動で見分ける）だけにキーがあり、体の他の骨にキーが無いフレームは、その手足の位置と向きだけを Kimodo の手足の制約（left-hand / right-hand / left-foot / right-foot）で合わせ、体は任せる。Kimodo の仕組み上、そのフレームの腰の位置・高さ・向きも一緒に合う（手足の位置は腰から見た値で表すため）。例: 30F 毎に全身のポーズ、その間の 15F に腕の IK だけで手を上下 → 30F 毎はポーズどおり、15F は手が打った位置を通り、体の揺れはプロンプトから
- **全ての親は読むだけでキーは打たない**。全ての親だけにキーがあるフレーム（体のキーが無いフレーム）は「腰がそこを通る」目印になる。例: 0F に立ちポーズ、全ての親を 40F・80F・120F で S 字に動かす → S 字に走る動きになる（体の姿勢は Kimodo 任せ）。全ての親のキーに回転が入っている時は、腰の向きも合わせる（例: 全ての親を 15F 毎に 180° 回す → くるくる回る。向きのずれ 1〜29°）。回転が無い時は位置だけ（毎回正面を向かせないため）

## モデルの作りへの対応（配布前提の汎用の作り・11-03）
ボーン名や親子を決め打ちせず、PMX の親子・付与・IK を読んで決める（`Retargeter._plan_writes`）。
- **同じ名前のボーン（11-06・スコープドッグ 21C+）**: センターが 2 本（[1] 体・[160] ライフルの持ち手。表示枠には無い）。名前の引き当てが後ろ（ライフル）を拾い、ライフルの骨を基準に体の位置を計算して、体が上に飛んでいた（行き帰りのずれ 60.73 → 直して 0.0）。MMD は VMD を読み込む時に同じ名前のキーを全部前の方の骨に入れる（同じフレームなら後のキーが勝つ）ので、生成や「元に戻す」のたびに体のセンターの 0F にライフルの値が入り、ライフルのキーは消えていた。名前は前の方を引き（`MMDSkeleton.index`）、読む時に 2 本目以降（VMD の名前＝先頭 15 バイトが同じ）のキーを外してログで知らせる（`MotionReader.read` → `Motion.dropped`）。2 本目のキーは VMD では戻せない
- **無いボーン（11-06 マスター「無いなら無いで無視（ログに警告）」）**: SOMA の関節に当てる骨（`SOMA_TO_MMD`）が無ければ飛ばす。MMD → SOMA ではいちばん近い（ある）祖先の向きを使い、SOMA → MMD では書かない（ほかの骨は全体の向きで合わせるので、向きは変わらない）。上半身2 が無ければ、書き戻しで Chest（背骨の曲がりの合計）の向きを上半身に入れる。止めるのは センター・下半身・左右どちらの脚（足・ひざ・足首）もそろわない時だけ（体の位置を書く先・SOMA の腰の根っこ・体格の比）。脚の付け根は片方だけでも腰の位置を合わせる。足ＩＫ・つま先ＩＫを探していた確認は、結果をどこにも使っていなかったので外した（IK の無いモデルが止まっていた）。確かめ（Tda ミクの名前を隠してまねた）: 全部ある時は直す前と差 0、上半身2・首・右腕・左ひじと手首・右脚を外しても、残った骨の向きは Kimodo の姿勢と 0.0°
- **向きの合わせ方**: 骨ごとに「欲しい世界の向き」を出し、MMD と同じ計算順で、親の実際の向き（間に挟まった機構のボーン・付与・目線や機構の IK 込み）を見てキーの回転を決める（`MMDSkeleton.pose(world_targets=…)`）。「肩の子は腕」のような標準の親子を前提にしない
- **付与の受け渡し元**: 腕・ひじなどが付与（回転・割合 1）で別のボーンから回転を受け取り、その受け渡し元が IK の鎖になっているモデル（ノイニクの「腕IK上腕・腕IK」）は、回転を受け渡し元に入れて、腕・ひじ自身は 0 にする。腕の IK の目標をつまんで動かすと手が素直についてくる
- **目標を置く IK**: 書いた骨か受け渡し元を鎖に含む IK（足ＩＫ・つま先ＩＫ・腕の IK など）は、目標を鎖の先が FK で届いた位置に毎フレーム置く（MMD の IK は何も動かさない状態になる）。それ以外の IK（目線・機構）はマスターのキーのまま
- **長い名前のボーン**: VMD の名前は 15 バイトまでで、MMD は文字の途中でも切る。読んだキーは元のバイト列のまま書き戻し、切れた名前は PMX のボーンに当て直す（ノイニクで 14 本、腰キャンセル・機構の IK などが当たらず無視されていた）。15 バイトで切ると同じ名前になる別々のボーン（「右機構-肩XキルIK」「…IK制御」「…IK2」）は VMD では区別できない（MMD 自身の保存・読み込みでも同じ）
- **キーのフレームを守る**: 書き戻す骨でキーのフレームにキーが無いものは、元の値でキーを足す（無いと前後の生成フレームから補間され、受け渡し元で腕の回転が二重になる）
- 確認（11-03）: 「MMD と同じ計算 → 読む → 書き戻す → MMD と同じ計算」の往復で、Tda ミク（ダンスの 5 フレーム）・ノイニク（しゃがんで棒を握るポーズ）とも関節の位置のずれ 0.00cm。ノイニクで生成（0F・30F のキー）すると、キーのフレームは元と 0.00cm、間のフレームは腕の直接の回転 0・IK が動かす量 0.00cm。ノイニクの腕の IK の目標を棒に沿って ±7cm 動かすと手首も ±0.74 単位ついてくる（手の向きは前腕につられて 15° 変わる）

## 計算の方式（11-10・0.3.0。NVIDIA 以外の GPU でも動かす）

Kimodo と MotionBricks を、3 つの方式のどれかで動かす。`work\paths.json` の `kimodo_backend`・`motionbricks_backend`（`paths.backend`）。
書いていなければ cuda（0.2.x までの環境はそのまま）。

| 方式 | Kimodo | MotionBricks |
|---|---|---|
| cuda | PyTorch の CUDA（今まで） | 公式のエンジン（TensorRT） |
| directml | 2 つの Transformer だけ ONNX Runtime の DirectML（`tools/kimodo_ort.py`）。残りは PyTorch の CPU | ONNX Runtime の DirectML（`tools/mb_ort.py`）。前後の計算（Warp）は CPU |
| cpu | PyTorch の CPU | ONNX Runtime の CPU |

- **決め方**: セットアップの試しの生成（`steps.try_backends`）が cuda（nvidia-smi がある時だけ）→ directml → cpu の順に試し、通った方式を
  `setup_state.json`（`_backend_kimodo`・`_backend_motionbricks`）と窓の `paths.json` に書く。GPU の世代は決め打ちしない
  （今の PyTorch や TensorRT で動かない NVIDIA の GPU も、ここで directml に落ちる）。強制終了（終了コード 0xC0000005）も「失敗」として次へ進む
- **GPU を替えた時**: 試しの生成の段の版に GPU の名前の印（`steps.gpu_tag`）を混ぜてあるので、セットアップが「更新があります」になり、方式を選び直す
- **常駐への渡し方**: 環境変数 `AINAKAWARI_BACKEND`（`pipeline.kimodo_env`・`smooth_stop._run`）。Kimodo には書き出す ONNX の置き場 `AINAKAWARI_ORT_CACHE`（`<kimodo>\ort_cache`）も
- **試す時**: 窓のプロセスに `AINAKAWARI_BACKEND=directml` を付けると、設定より先にそれを使う。セットアップの試す順は `AINAKAWARI_SETUP_BACKENDS=directml,cpu`
- **入れる物**: `installer\ort-kimodo.txt`（onnxruntime-directml 1.23.0・onnx 1.23.2。Python 3.10）と `ort-motionbricks.txt`（1.24.4・1.23.2。Python 3.12）。
  版と sha256 つき。今ある numpy などの版を動かさないよう、環境の今の版を制約にして `uv pip compile` で作った（頭の行に作り方）。どの方式の PC にも入れる（約 60MB）
- **GPU の診断**（`gpu.py`）: cuda は今までどおり nvidia-smi。それ以外は、レジストリのディスプレイ アダプターから名前と VRAM（`HardwareInformation.qwMemorySize`）を読む

### Kimodo を ONNX にする所（`tools/kimodo_ort.py`）
- 時間のほとんどは、ノイズ除去 1 回ごとに呼ばれる 2 つの Transformer（腰用・体用。各 16 層・約 1.4 億個の重み）。この 2 つだけを ONNX（各約 580MB）に書き出し、
  モデルの中の部品を `OrtBlock` に差し替える。100 回のループ・CFG・キーの条件・後処理は Kimodo のコードのまま
- **書き出しで踏んだ物**（順に）: ① PyTorch の Transformer の近道（`aten::_transformer_encoder_layer_fwd`）は書き出せない
  ② マスクを渡す経路は、書き出した時のフレーム数が焼き付く ③ マスクを外しても、`nn.MultiheadAttention` の中の view に「長さ」「人数×ヘッド数」が焼き付く（76×24×128）。
  → 同じ重みで注意機構を書き下した（`_Exportable._encoder`。形を数字で指定せず、最後の次元をヘッドに割るだけ。掛け算は全部 4 次元）
- **検算**: 書き下した計算が元の `forward` と同じかを、書き出す前に倍精度で比べる（差 1e-12）。単精度だと元の計算どうしでも 1e-3 ずれるので、違いと見分けられない
- **形**: ONNX Runtime は形を決めて開いた方が速いので、(人数, フレーム数) ごとに開き、直近 2 つを覚える。新しい長さの最初の 1 回は約 6 秒遅い
- **AIナカワリの使い方に限った作り**: 1 回に 1 本だけ作る（マスクは常に「全部使う」）・文の並びは 1 個。違う使い方が来たら止める

### MotionBricks を ONNX Runtime で動かす所（`tools/mb_ort.py`）
- TensorRT に触っているのは `motionbricks.inference.engine.InferenceEngine` の 1 クラス。その口（`device_tensor`・`enqueue_async` など）を `OrtSOMAEngine` で全部上書きする。
  公式のコードは無改造。`tensorrt` が入っていない・読めない PC でも読めるよう、空の `tensorrt` を先に置く（だから motionbricks より先に import する）
- 入出力の置き場は Warp の CPU の配列で、numpy と同じメモリ。姿勢の詰め替え・端の合わせ込みは公式の Warp のカーネルを CPU で動かす
- **DirectML は MatMul を 4 次元までしか受けない**。このモデルには 5 次元（[1, 姿勢, 30 関節, 3, 3]）の MatMul が 4 個あり、そのままだと 80070057 で落ちる。
  先頭の 1 を Squeeze で外して掛け、Unsqueeze で戻した ONNX を初回に作る（`.ort-cache`。どれが 5 次元かは CPU で 1 回動かして実際の形を見る）
- ONNX Runtime は DirectML で開けないと**黙って CPU に落ちる**。開いた方式を確かめて、違えば止める（2 つのエンジンとも）

### 測った数字（RTX 3090・Core i7-12700F・11-10）

| | cuda | directml | cpu |
|---|---|---|---|
| Kimodo 67 フレーム | 3.1 秒 | 3.2 秒 | 39〜50 秒（PyTorch。ONNX Runtime の CPU だと 155 秒） |
| Kimodo 300 フレーム | 7.4 秒 | 7.2 秒 | 137〜229 秒 |
| Kimodo の VRAM・メモリ | 1.1GB・1.5GB | 1.4GB・3.1GB | 0・1.8GB |
| MotionBricks 81 フレーム（3 区間） | 0.41 秒 | 0.43 秒 | 0.56 秒 |
| MotionBricks の推論 1 回 | 3.5 ミリ秒 | 9 ミリ秒 | 40 ミリ秒 |

動きの差: Kimodo の directml と PyTorch の CPU は回転で最大 0.006 度（同じ種）。cuda とは乱数の出どころ（GPU か CPU か）が違うので、同じ種でも別の動きになる。
MotionBricks の directml・cpu と TensorRT は回転で 0.03〜0.11 度（TensorRT が TF32 で精度を落としている分）、directml と cpu の間は 0.05 度未満。

**確かめていない物**: AMD・Intel・GTX 10 シリーズの実機（3090 を DirectML で動かした所まで）。NVIDIA の PC で `CUDA_VISIBLE_DEVICES=-1` を付けると DirectML ごと落ちる（GPU なしの真似には使えない）。

## 生成の中断（11-10・0.3.0）
- 窓とパネルの「生成」は、生成中は「中断」になる（`App._generate_or_cancel`）。押せるのは MMD に書き戻す前まで（`runner.generate` の `on_commit`）
- 生成のスレッドは `resident.cancellable(印)` の中で回る。印が立つと、切れ目（`resident.check_cancel`）・常駐の立ち上げ待ち・答え待ちで `resident.Cancelled`
- 作っている途中の常駐には、頼んだ接続にそのまま `{"cancel": True}` を送る。常駐は Kimodo がノイズ除去の 1 回ごと、MotionBricks が目標ごとに `conn.poll(0)` で見て、
  やめたら `{"ok": False, "cancelled": True}` を返して次の依頼を待つ（常駐は落とさない）。頼んだ側がいなくなった時もやめる
- Kimodo（e1c219c）の `_multiprompt` は `progress_bar` を内側の `_generate` に渡していない。生成の間だけ `model._generate` に差し込む（`kimodo_gen.generate`）

## MMD の癖（作る時に踏んだもの）
- **VMD の読み込みは足し込み**（ファイルにあるキーだけ上書きし、他のキーは残す）→ 読み込む前に「全ﾌﾚｰﾑ」を範囲選択してキーを全部消し、まるごとのモーションを読み込む。11-03 の昼まで「丸ごと入れ替わる」と誤解していて、「元に戻す」で生成した間のキーが残る状態だった（直した）

- 足ＩＫの親は全ての親ではなく**足IK親**（Tda ミク）。11-03 の昼までは足IK親が 0 の前提で書いていて、足IK親ごと動かしたモーションでは足ＩＫが最大 3m 先に行っていた（直した）

- 標準・準標準のボーン名が前提（下半身・上半身・上半身2・首・頭・肩・腕・ひじ・手首・足・ひざ・足首・つま先・足ＩＫ・つま先ＩＫ）。無いモデルはエラーで止める

- マスターがすでに打ったキーのフレームは、腕に直接回転が入っていればそのまま（IK の形には組み直さない）。生成したフレームだけが IK の形になる
- **物理演算をオフにしたキー**: メモリのどこに入っているか分かっていない。メモリから読む控えは、補間の物理演算の印を全部「オン」（0・0）で書くので、物理演算をオフにしたキーがある場面では、生成や「元に戻す」でオフが消えるおそれがある（未確認）
